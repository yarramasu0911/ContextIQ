Why — the problem

RAG systems in 2026 still hit the same six failure modes. Our project addresses all of them.

ProblemWhat we do about it
Pure dense search misses exact keywordsHybrid BM25 + dense via Reciprocal Rank Fusion
Similar-looking top-k, LLM picks wrong chunkCross-encoder reranker (ms-marco-MiniLM)
Vague / follow-up questions don't retrieveQuery rewriting, HyDE, multi-query (opt-in)
Hallucinations go undetectedPer-sentence grounding check → inline [unverified]
Repeated questions waste tokens & timeSemantic Q&A cache (0.95 cosine threshold)
No regression visibility when we change configsRAGAS-style evaluation harness + audit log

End-to-end pipeline. Important details: role filter applies at both retrieval stores; parent-document pattern means we embed small chunks but generate from larger parents.

How — the chunking hierarchy

LEVEL 0 · DOCUMENT        whole uploaded file
            ▼   extract (pdfplumber + OCR fallback, openpyxl, python-pptx, …)
LEVEL 1 · SENTENCE        sentence-level split
            ▼   group by semantic similarity (θ = 0.45) + per-type size caps
LEVEL 2 · CHUNK           ← embedded + indexed + reranked
            ▼   glue neighbor chunks (parent_window)
LEVEL 3 · PARENT          ← what the LLM actually sees

Retrieve small

Level-2 chunks (~300 tokens) are what get embedded and reranked. Small chunks = sharp similarity signal = better precision.

Generate large

Level-3 parents (chunk + neighbors) are handed to the LLM. More context per source = more complete, grounded answers.

The small-for-retrieval / large-for-generation split is the key architectural lever that makes everything else work. Chunk sizes are per-extension.

Challenges & plan forward 3 pts

Challenge 1: flan-t5-base's short answers drag faithfulness score to 0.
Its outputs are so terse that sentence embeddings don't cosine-match the long source chunks.
▸ Plan: default to flan-t5-large before demo day; add OpenAI path with gpt-4o-mini as the "quality" config. Both already wired.
Challenge 2: chunk size tuning is a blind guess without re-ingestion.
Changing _CHUNK_SIZE_BY_EXT requires clear + re-upload — friction to A/B test.
▸ Plan: build a one-shot /admin/reingest endpoint that walks data/uploads/ and re-chunks everything under the current config.
Challenge 3: BM25 is in-memory; restarts are slow with 1,800+ chunks.
Startup BM25 rebuild from Pinecone takes ~30 s.
▸ Plan: persist the tokenized corpus + IDF stats to data/bm25.pkl; startup loads the pickle and diffs against Pinecone instead of full rebuild.
Challenge 4: evaluation harness has no LLM-as-judge.
Embedding-based faithfulness misses subtle hallucinations.
▸ Plan: add gpt-4o-mini judge for faithfulness + relevance metrics; cheap enough to run on every eval. Keep embedding-based as the free baseline.
Four concrete obstacles, each with a specific fix and a rough effort estimate. Nothing here blocks demo day — all are improvements on a working system.

Anticipated Q&A

Questions reviewers can answer directly from this deck:

Who is this for?
Enterprise teams with three-tier access needs — admins, HR, general users — who want to query internal documents with grounded answers.

What makes this different from a generic RAG demo?
Role-based visibility enforced at the vector store, hybrid BM25 + dense retrieval, cross-encoder reranking, parent-document retrieval, and runtime faithfulness checks with inline citations.

Why hybrid retrieval?
Pure dense search misses exact-match keywords (names, IDs, acronyms). BM25 catches those. RRF fusion is rank-based so the two score scales don't conflict.

How do you measure progress?
RAGAS-style harness: context recall/precision, answer similarity, faithfulness. Plus latency and cache-hit rate. Run on a gold JSON set any time we change configs.
